## Source of truth

The canonical application version source is `VERSION.json`.

Current release metadata:

- version: `0.9.0`
- release date: `2026-08-25`
- release candidate base: `3677b1d7231df67db8ef4cd2fa2fb761c2f293ce`
- final release SHA: pending merge

Runtime identity is composed from:

- version: `VERSION.json`
- release date: `VERSION.json`
- build commit: `getBuildInfo().commit`
- build time: `getBuildInfo().buildTime`

`src/lib/app-version.ts` imports `VERSION.json` and exposes `APP_VERSION`,
`APP_RELEASE_DATE` and `APP_RELEASE`. Do not create a second editable version
constant.

`src/lib/build-info.ts` remains the source for build metadata. It preserves this
priority order:

1. `NEXT_PUBLIC_APP_COMMIT` / `NEXT_PUBLIC_APP_BUILD_TIME`;
2. `.build-meta.json` generated by `scripts/prepare-build-metadata.mjs`;
3. local git fallback for commit;
4. `unknown`.

`package.json.version` was historically used for Beta `0.6.0` metadata. From this
policy onward, it is not the public release source of truth unless a future release
explicitly aligns it with `VERSION.json`.

## Semantic versioning

Application releases use simple Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

PATCH: corrections without relevant functional change.

MINOR: compatible functionality, UX or product change.

MAJOR: incompatible product/contract change or a formal 1.0+ milestone.

While the product remains pre-1.0, releases use:

```text
0.x.y
```

## Release procedure

Each new release must:

1. determine the SemVer bump;
2. update `VERSION.json.version`;
3. update `VERSION.json.releaseDate`;
4. update `docs/02-delivery/change-log.md`;
5. run the required validations for the release scope;
6. merge through the approved release path;
7. register the final release SHA;
8. build the runtime with coherent build metadata;
9. visually verify that `ReleaseStamp` shows version, release date and SHA;
10. deploy through the corresponding Canary or production procedure.

## Versioning precheck

Before a release merge, Canary promotion, production deploy or hotfix, verify:

- `CURRENT_APP_VERSION` from `VERSION.json`;
- `CURRENT_RELEASE_DATE` from `VERSION.json`;
- `CANDIDATE_SHA` from the target branch or commit;
- compatibility with the change type and SemVer bump.

After merge, register:

- `FINAL_RELEASE_SHA`.

After deploy, verify:

- the visible `ReleaseStamp`;
- runtime SHA equals the expected release SHA;
- build time is present and coherent.

## Critical rule

Never reuse the same version number for two different releases.

Never modify an already published version retroactively.

A rebuild of the same code may keep version and release date, but it will have a
different build time.

A later functional change requires a new version.
