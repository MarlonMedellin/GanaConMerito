# MVP/Product Direction Audit — 2026-05-07

## 1. Executive Summary
GanaConMerito **sí tiene un MVP funcional operativo** (login → onboarding → práctica → dashboard) y un componente Tutor GCM en modo restringido. El principal riesgo no es técnico de implementación base, sino **de enfoque de producto**: el backlog y la narrativa estratégica mezclan objetivos de operación interna, cumplimiento documental y expansión funcional sin una jerarquía clara de validación de negocio.

Conclusión ejecutiva: el producto debe entrar en un ciclo corto de **validación de valor real de práctica + aprendizaje** antes de seguir invirtiendo en expansión (editorial, analítica avanzada, LLM real, personalización profunda).

Estado recomendado: **needs-fix** (no-go parcial a expansión; go condicionado a foco MVP).

---

## 2. MVP Definition

### MVP real (hoy)
- Usuario autenticado puede entrar, completar onboarding, resolver preguntas en práctica y ver feedback/métricas en dashboard.
- Tutor GCM acompaña la práctica con guardrails y sin autoridad sobre scoring o avance.

### Usuario objetivo (actual inferido)
- Aspirante que necesita practicar con preguntas tipo concurso/selección y recibir retroalimentación útil para mejorar desempeño por sesión.

### Dolor principal
- Falta de práctica estructurada con señal clara de progreso y retroalimentación accionable, sin falsas promesas analíticas.

### Propuesta de valor (MVP)
- “Te ayudamos a practicar de forma guiada y trazable, mostrando progreso útil y prudente para mejorar tu preparación.”

### Evento de activación
- Primera sesión de práctica completada con al menos 1 respuesta enviada y visualización del dashboard de sesión.

### Core loop
1. Usuario inicia sesión.
2. Completa onboarding mínimo.
3. Responde ítems en práctica.
4. Recibe feedback inmediato + apoyo Tutor GCM.
5. Revisa dashboard.
6. Vuelve a práctica para mejorar.

### Journey núcleo (happy path)
- Login → onboarding → start session → answer/advance → tutor consult (opcional) → dashboard sesión → nueva sesión.

### MVP vs post-MVP
**MVP (debe mantenerse):**
- Auth estable.
- Flujo práctica extremo a extremo.
- Dashboard prudente (sin claims fuertes).
- Tutor GCM con guardrails estrictos.

**Post-MVP (debe congelarse temporalmente):**
- LLM real en producción con mayor autonomía.
- Personalización pedagógica avanzada por perfil/concurso.
- Analytics predictivas/longitudinales fuertes.
- CMS/editorial multiusuario completo.
- Expansión grande de frentes no ligados a activación/retenCIÓN.

## 3. Critical Risks

1. **Riesgo de foco**: coexistencia de múltiples frentes (normativo, runtime, editorial, tutor, CI, refactors) sin priorización explícita por impacto en usuario final.
2. **Riesgo de valor no validado**: falta de métricas de activación/retención claramente instrumentadas para demostrar que el loop de práctica genera hábito.
3. **Riesgo de sobrepromesa**: tensión entre capacidades prudentes actuales y posibles lecturas de “inteligencia avanzada” del tutor/dashboard.
4. **Riesgo de dependencia normativa**: estado `synthesized_governed_unverified` limita confianza para ciertas funcionalidades del Tutor GCM.
5. **Riesgo operativo-documental**: fuerte disciplina de gobernanza, pero posible costo de ejecución alto si reemplaza validación de mercado.

---

## 4. Scope Reduction Recommendations

1. **Congelar 6–8 semanas** todo trabajo que no impacte activación, completion de sesión y retorno a práctica.
2. **Reducir Tutor GCM al rol MVP estricto**: aclaración, guía de razonamiento y explicación post-respuesta; sin expandir capacidades conversacionales.
3. **Posponer editorial como frente de producto** y tratarlo como soporte interno/solo lectura.
4. **No iniciar analytics nuevas** hasta tener baseline robusta de cohortes básicas y retención por semana.
5. **Evitar refactors “por limpieza”** salvo bloqueos directos de estabilidad del flujo core.
6. **Limitar backlog inmediato a 3 outcomes**:
   - subir activación,
   - subir finalización de sesión,
   - subir retorno semanal.

## 5. Metrics & Validation Plan

### Métricas de éxito (MVP)
- **Activation Rate**: % usuarios nuevos que completan onboarding + primera sesión en <24h.
- **Session Completion Rate**: % sesiones iniciadas que llegan a cierre.
- **D1/D7 Return to Practice**: % usuarios que vuelven a práctica al día 1 y día 7.
- **Tutor Assisted Resolution Rate**: % turnos con uso de tutor que terminan en respuesta enviada (sin abandono).
- **Time to First Value**: minutos desde login hasta primera respuesta evaluada.

### Condiciones de falla (failure conditions)
- Activación baja sostenida (<objetivo acordado 2–3 sprints).
- Alto abandono entre onboarding y primera respuesta.
- Uso de tutor sin mejora en completion o retorno.
- Métricas de dashboard no correlacionan con reenganche.

### Supuestos clave a validar
- Que feedback + tutor aumenta continuidad de práctica.
- Que el dashboard prudente aporta motivación real y no ruido.
- Que el usuario entiende el valor en la primera sesión.

### Validaciones faltantes
- Cohortes por canal/perfil con comportamiento real.
- Entrevistas breves de usuarios que abandonan en onboarding/práctica temprana.
- Experimentos simples de UX de activación (copys/CTA/primera tarea).

### Dependencias técnico-producto críticas
- Persistencia de trazas mínimas para medir loop (sin esto no hay aprendizaje de producto).
- Instrumentación analítica confiable por evento de journey.
- QA mínima automatizada del flujo login→práctica→dashboard para evitar regresiones de negocio.

---

## 6. Go/No-Go Recommendation

### Recomendación
**PAUSE parcial de expansión + GO condicionado de MVP.**

Interpretación práctica:
- **GO** para invertir en mejoras que aumenten activación, completion y retención del flujo core.
- **NO-GO temporal** para expansión de features post-MVP (LLM real, personalización profunda, editorial productizada, analytics complejas).

Criterio para salir del estado “needs-fix”:
- 2 ciclos de medición con mejora verificable en 2 de 3 métricas núcleo (activación, completion, retorno).
